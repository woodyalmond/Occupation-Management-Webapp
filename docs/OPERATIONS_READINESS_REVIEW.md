# Alarmapp 운영 레벨 적합성 검토

작성일: 2026-04-30

## 결론

현재 `alarmapp`는 개인이 로컬에서 매일 쓰는 작업 관리 도구로는 운영 직전 단계에 가깝다. 핵심 이유는 할일 생성, 완료 처리, 활동 기록, 날짜별 조회, 알람, 로컬 데이터베이스 저장, Markdown 내보내기까지 이미 일상 운영의 기본 흐름이 연결되어 있기 때문이다.

다만 팀 단위 또는 장기간 장애 없이 쓰는 운영 레벨 제품으로 보기는 아직 이르다. 반복 일정, 검색과 필터, 백업과 복구, 실패 알림, 데이터 이관, 권한, 관측성(시스템이 잘 도는지 보는 장치)이 부족하다.

따라서 판단은 다음과 같다.

- 개인 로컬 사용: 조건부 적합
- 1인 개발자의 매일 기록/할일 관리: 적합에 가까움
- 팀 협업 작업 관리: 부적합
- 외부 사용자에게 배포하는 운영 서비스: 아직 부적합

## 운영 레벨의 최소 의미

여기서 운영 레벨은 “기능이 많다”가 아니라 “매일 써도 기록이 잃어버려지지 않고, 중요한 일을 놓치지 않으며, 문제가 생겼을 때 복구할 수 있는 상태”를 뜻한다.

원자 단위로 쪼개면 다음 다섯 가지다.

- 기록성: 사용자가 한 일과 해야 할 일이 남아야 한다.
- 실행성: 오늘 무엇을 해야 하는지 바로 보여야 한다.
- 알림성: 놓치면 안 되는 일을 알려줘야 한다.
- 복구성: 장애나 실수 후에도 데이터를 되살릴 수 있어야 한다.
- 확장성: 기록이 늘어나도 찾고 정리할 수 있어야 한다.

## 외부 기준 조사 요약

Firecrawl로 확인한 대표 기준은 다음과 같다.

- Todoist는 빠른 할일 입력, 반복 마감일, 알림, 프로젝트, 우선순위, 라벨, 필터, 오늘 보기, 예정 보기, 협업, 생산성 통계를 주요 기능으로 제시한다. 출처: [Todoist Features](https://www.todoist.com/features)
- Microsoft To Do는 마감일, 알림, 반복 설정, 상세 보기처럼 개인 할일 관리의 기본 흐름을 강조한다. 출처: [Microsoft To Do due dates and reminders](https://support.microsoft.com/en-us/office/add-due-dates-and-reminders-in-microsoft-to-do-064d9696-08d1-4433-bfdd-f661dc97491f)
- Asana는 리스트, 보드, 캘린더, 타임라인, 담당자, 의존성(다른 일이 끝나야 시작할 수 있는 관계), 자동화, 시간 추적을 작업 관리의 상위 기능으로 제시한다. 출처: [Asana Task Management](https://asana.com/uses/task-management)
- NN/g는 복잡한 앱에서 중요한 정보가 눈에 띄어야 하고, 사용자가 흐름을 잃었을 때 다시 이어갈 수 있어야 하며, 기능을 줄이지 않으면서 화면 잡음을 줄여야 한다고 설명한다. 출처: [8 Design Guidelines for Complex Applications](https://www.nngroup.com/articles/complex-application-design/)
- Ink & Switch의 local-first(로컬 우선, 내 컴퓨터 저장을 기본으로 하는 방식) 원칙은 데이터 소유권, 오프라인 접근, 내보내기, 장기 보존, 개인정보 보호를 중요하게 본다. 출처: [Local-first software](https://www.inkandswitch.com/essay/local-first/)

## 현재 기능 평가

### 이미 운영에 가까운 부분

현재 앱은 “오늘 무엇을 했고 무엇을 해야 하는가”라는 개인 운영의 핵심 질문에 답할 수 있다.

- MariaDB 저장으로 브라우저 새로고침 후에도 작업과 활동 기록이 유지된다.
- API가 할일과 활동의 CRUD(생성, 조회, 수정, 삭제)를 제공한다.
- Flutter Web UI가 로컬 API와 연결되어 작업을 직접 조작할 수 있다.
- Docker Compose로 MariaDB, API, Web UI를 함께 띄울 수 있어 실행 절차가 단순하다.
- 타이머와 알람이 있어 “시간이 지나면 기록한다”는 사용 습관을 만들 수 있다.
- 기록 탭에 날짜 선택 UI가 있어 특정 날짜의 활동과 할일을 볼 수 있다.
- 완료된 할일에 취소선이 표시되어 상태 차이가 눈에 들어온다.
- 활동 기록에 시작 시각이 뱃지 형태로 보이므로 하루 흐름을 복기하기 좋다.
- Daily Note Markdown 저장으로 하루 기록을 파일로 남길 수 있다.

이 정도면 단순 투두앱이 아니라 “개인 작업 로그”에 가깝다. 특히 활동 기록과 Daily Note 내보내기는 일반 할일 앱보다 개인 회고에 더 강하다.

### 운영 레벨로 보기 어려운 부분

현재 가장 큰 약점은 “데이터를 계속 믿고 쓸 수 있는가”와 “기록이 많아졌을 때 찾을 수 있는가”다.

- 자동 백업이 없다. MariaDB 볼륨이 깨지거나 삭제되면 복구 경로가 약하다.
- Markdown 내보내기는 좋지만, 이것은 백업의 일부일 뿐 DB 전체 복구 방식은 아니다.
- 반복 작업이 없다. 매일/매주 해야 하는 루틴 작업을 자동 생성하지 못한다.
- 알림이 타이머 중심이다. 특정 할일의 마감 시각 알림과 반복 알림은 아직 약하다.
- 검색과 고급 필터가 없다. 기록이 1000개 이상 쌓이면 과거 기록을 찾기 어렵다.
- 우선순위, 라벨, 프로젝트가 없다. 일이 많아지면 “무엇부터 할지” 정렬하기 어렵다.
- 활동 기록과 할일 사이의 명시적 연결이 약하다. 어떤 활동이 어떤 할일을 처리한 것인지 추적하기 어렵다.
- 오류 관측성(에러 로그, 상태 확인, 실패 알림)이 최소 수준이다.
- API 인증이 없다. 로컬 전용이면 괜찮지만, 네트워크에 열면 위험하다.
- 팀 협업 기능이 없다. 담당자, 댓글, 권한, 공유 프로젝트가 없다.

## 기준별 판단

### 1. 개인 실행 관리

판단: 적합에 가까움

할일 생성, 완료 처리, 날짜별 보기, 타이머, 활동 기록이 연결되어 있어 개인이 하루를 운영하는 데 필요한 기본 축은 있다. 지금 상태로도 “오늘 할 일 적기, 타이머 돌리기, 실제 한 일 기록하기, 하루 기록 Markdown으로 남기기”가 가능하다.

보완하면 좋은 점은 반복 할일과 우선순위다. 사람은 매일 같은 일을 반복하는 경우가 많고, 급한 일과 중요한 일을 구분해야 하기 때문이다.

### 2. 기록 보존

판단: 조건부 적합

MariaDB와 Markdown 저장이 있으므로 기록은 남는다. 특히 Markdown은 사람이 직접 읽을 수 있는 형식이라 장기 보존에 좋다.

하지만 운영 레벨에서는 “저장된다”만으로 부족하다. 백업, 복구, 내보내기, 가져오기까지 있어야 한다. 현재는 `papers/dailynote`에 날짜별 결과물이 남지만, DB 전체를 복원하는 표준 절차는 문서화되어 있지 않다.

### 3. 사용성

판단: 개인 사용 기준 적합, 대량 데이터 기준 미흡

날짜별 기록 UI, 활동 시각 뱃지, 완료 취소선은 중요한 정보를 눈에 띄게 만든다. 이는 NN/g가 말하는 “중요 정보의 시각적 강조”와 맞다.

다만 데이터가 많아지면 검색, 필터, 정렬, 그룹화가 필요하다. 지금은 날짜 중심으로만 접근하므로 “지난달에 어떤 개발 작업을 했지?” 같은 질문에는 약하다.

### 4. 알림과 실행 유도

판단: 부분 적합

타이머 기반 알림과 사운드 활성화 흐름은 현재 앱의 강점이다. 브라우저 정책 때문에 사용자 상호작용이 필요하다는 점을 UI에서 다루고 있는 것도 좋다.

하지만 작업 관리 프로그램 관점에서는 “마감일 기반 알림”과 “반복 알림”이 필요하다. Microsoft To Do와 Todoist 모두 마감일과 알림을 핵심 기능으로 둔다.

### 5. 로컬 우선성

판단: 방향은 적합, 복구성은 부족

로컬 MariaDB, 로컬 API, Docker Compose 실행, Markdown 내보내기는 local-first 방향과 잘 맞는다. 사용자가 데이터를 자기 컴퓨터에 갖는다는 점도 좋다.

하지만 local-first의 핵심은 “내 컴퓨터에 있다”에서 끝나지 않는다. 내보내기, 백업, 장기 보존, 장애 복구까지 있어야 한다. 현재는 내보내기는 있으나 복구 절차가 약하다.

### 6. 팀 운영

판단: 부적합

Asana 같은 팀 작업 관리 도구는 담당자, 권한, 댓글, 의존성, 여러 보기, 자동화가 핵심이다. 현재 앱은 개인 작업 흐름에 맞춰져 있으므로 팀 운영 도구로 보기는 어렵다.

이것은 단점이라기보다 제품 방향의 차이다. 지금 앱은 팀 협업보다 “개인 작업 기록과 루틴 실행”에 집중하는 편이 낫다.

## 우선순위 제안

운영 레벨에 가까워지려면 다음 순서가 좋다.

1. 자동 백업과 복구 문서화

가장 먼저 해야 한다. 데이터가 사라지면 작업 관리 도구의 신뢰가 깨진다. `mariadb` 볼륨 백업, Markdown 백업, 복구 절차를 README에 넣어야 한다.

2. 반복 할일

매일, 매주, 매월 반복되는 작업을 자동으로 생성해야 실제 생활 운영에 가까워진다. Todoist와 Microsoft To Do도 반복 설정을 핵심 기능으로 둔다.

3. 검색과 필터

카테고리, 날짜 범위, 상태, 키워드로 활동과 할일을 찾을 수 있어야 한다. 기록이 쌓일수록 이 기능의 가치가 커진다.

4. 우선순위와 라벨

할일이 5개일 때는 필요 없지만, 30개가 넘으면 필수다. “오늘 반드시 할 일”과 “언젠가 할 일”을 구분해야 한다.

5. 마감일 기반 알림

타이머 알림과 별도로, 특정 할일의 마감 시각을 기준으로 알림이 필요하다.

6. 운영 상태 확인

API 상태, DB 연결 상태, Daily Note 저장 실패 여부를 UI에서 볼 수 있으면 좋다. 지금은 실패하면 사용자 경험이 끊길 수 있다.

## 최종 판단

현재 `alarmapp`는 “개인 로컬 작업 관리 + 활동 기록 + Daily Note 생성기”로 정의하면 방향이 좋고, 운영 레벨에 가까워지고 있다.

하지만 “운영 레벨 작업 관리 프로그램”이라고 부르려면 최소한 자동 백업, 반복 할일, 검색/필터, 마감 알림이 추가되어야 한다. 이 네 가지가 들어가면 개인용 운영 도구로는 충분히 강해질 수 있다.

팀 협업 제품으로 확장하는 것은 지금 단계에서는 추천하지 않는다. 그 방향은 기능 폭이 급격히 늘어나고, 인증, 권한, 공유, 충돌 처리, 동기화 같은 비용이 커진다. 지금은 개인 로컬 운영 도구로 좁게 잡는 편이 더 빠르고 실용적이다.

## 다음 구현 후보

가장 현실적인 다음 작업은 다음 하나다.

반복 할일과 자동 백업 중에서는 자동 백업을 먼저 권장한다. 이유는 단순하다. 반복 할일은 편의 기능이지만, 백업은 신뢰 기능이다. 작업 관리 도구에서 신뢰가 깨지면 나머지 기능이 좋아도 계속 쓰기 어렵다.
